# 架构决策记录（ADR）

格式：背景 → 决策 → 后果 → 放弃的选项。按时间顺序。

---

## ADR-001 离线优先的可运行性

**背景**：项目要给别人看、给面试官跑。任何"先配个 API Key 才能启动"的设计都会让 90% 的人停在第一步。

**决策**：抽象出 `ChatModel` 协议，提供两个实现——`MockChatModel`（确定性夹具）与 `OpenAICompatChatModel`；默认 `XM_LLM_PROVIDER=mock`，全链路（含评测、压测、CI）都能零密钥跑通。

**后果**：
- 正：CI 不需要密钥；测试完全确定；面试现场 30 秒能起。
- 负：离线输出质量不代表真实模型，所有质量结论必须标注模式（已在 README/EVALUATION 反复声明）。

**放弃**：只在单测里 mock、运行时强制真模型——复现成本太高。

## ADR-002 自实现 BM25 与哈希向量，不引入向量库

**背景**：语料 12 篇 / 24 块。引入 Chroma 或 FAISS 会带来进程模型、持久化目录、版本兼容三类成本，而收益在 24 块规模下接近零。

**决策**：BM25 用约 40 行实现并暴露原始分数；向量用带符号特征哈希（256 维）确定性生成；索引常驻内存，可 `save/load` 到 JSON。

**后果**：
- 正：零外部服务、可单测、融合分数完全可解释（`embed_score` / `lexical_score` 都在响应里）。
- 负：语义泛化弱于真 embedding，同义改写会掉分；规模到 10 万块需要换实现。

**放弃**：Chroma（依赖重）、`rank_bm25`（只差 40 行，但少了分数可见性）。

## ADR-003 引用由系统回填，模型只选编号

**背景**：让模型"写出来源"必然出现"看起来像但不在检索结果里"的幻觉来源。

**决策**：上下文按 `[n]` 编号，模型只输出 `【n】`；系统用正则抽取编号，从 `source_map` 回填 `doc_id/title/section/score`；越界编号剔除并记 `warnings`；完全没有引用则判定不可验证，直接拒答。

**后果**：
- 正："可溯源"变成可校验属性，能被单测钉住（越界、无引用、忠实度）。
- 负：模型必须遵守编号格式；不遵守时会退化成拒答（保守但安全）。

**放弃**：让模型输出 JSON 引用数组——格式错误率更高，且同样需要校验。

## ADR-004 增加"可答性门禁"，阈值由分布标定

**背景**：相似度阈值分不开"主题相关但无答案"的问题（U03 加拿大清关，检索分 0.3936，高于可答组最低 0.3509）。

**决策**：在生成前增加一道词面覆盖门禁：问题内容词（jieba 分词、去停用词）在证据中的 IDF 加权覆盖率低于 0.30 即拒答；OOV 词按最高权重惩罚。

**后果**：
- 正：4/6 不可答被拦下，且不产生模型调用。
- 负：仍是词面代理，两条例题漏网；对同义改写（"飞机" vs "登机"）不敏感。已在评测报告单列，并列为换 NLI judge 的触发条件。

**放弃**：只调相似度阈值——会同时误拒可答问题，指标双输。

## ADR-005 HITL 用两阶段状态机，而非阻塞式中断

**背景**：文案与选品是对外发布内容，必须人工确认。LangGraph 的 `interrupt` 需要 checkpointer，且进程重启后恢复语义复杂。

**决策**：图在 `hitl_gate` 返回 `awaiting_approval`，把**完整状态快照**写入 `tasks.output` 后结束本次调用；审批时读取快照，直接执行 `finalize`，不重跑检索与生成。

**后果**：
- 正：状态可持久化、可审计、可单测；重启不丢任务；审批不重复计费。
- 负：图被拆成"前半程/后半程"两个入口，逻辑上不如 interrupt 连贯；多步审批需要额外状态字段。

**放弃**：`interrupt` + Postgres checkpointer——v1.0 引入的复杂度大于收益。

## ADR-006 SQLite 单文件存储

**背景**：需要任务、幂等、记忆、审计四类持久化，但目标是单机可跑。

**决策**：一个 `Store` 类封装 SQLite（WAL、显式 SQL、行转模型），所有写操作带锁。

**后果**：
- 正：零运维、事务一致、备份就是复制文件。
- 负：并发写是瓶颈（实测 20 并发下 p95 200 ms），且无法多副本共享。已在 ARCHITECTURE 第 7 节给出扩容路径。

**放弃**：Postgres（单机部署成本）、内存字典（重启丢任务，HITL 不可用）。

## ADR-007 自研指标注册表

**背景**：只需要 counter/histogram/gauge 三种，且要能渲染 Prometheus 文本。

**决策**：`obs/metrics.py` 自实现约 180 行注册表，模块级导出规范指标名。

**后果**：
- 正：无第三方依赖、测试可直接断言渲染结果、指标名集中管理。
- 负：没有 exemplar、native histogram 等高级能力；多进程部署需要另行聚合。

**放弃**：`prometheus_client`（其实可以接受，但会多一个运行时依赖且默认注册表是全局的，不利于测试隔离）。

## ADR-008 前端不引入构建链

**背景**：控制台需要展示对话、Trace、指标，但项目定位是后端能力展示。

**决策**：原生 HTML/CSS/JS + SSE，由 FastAPI `StaticFiles` 托管，零 npm、零构建。

**后果**：
- 正：`git clone` 后无需 node；控制台与 API 同源，无 CORS 问题；调试直接改文件刷新。
- 负：组件化与类型安全弱于 Vue/React；复杂交互会难以维护。

**放弃**：Vue3 + Vite——与"克隆即跑"的目标冲突。
