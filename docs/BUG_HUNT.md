# 对抗性缺陷排查记录

> 目的：不是"再跑一遍测试"，而是主动构造会失败的输入，验证平台在并发、越界、跨接口一致性上的真实行为。
> 每一条都先在修复前复现（记录实际输出），再补回归测试。回归测试见 `tests/test_regressions.py`。

## 方法

| 手段 | 用在哪些地方 |
|---|---|
| 并发（`asyncio.gather` / 多线程） | 幂等键、审批、指标计数 |
| 越界输入 | 5 MB 请求体、空 `q`、`top_k=0/999`、`limit=0` |
| 跨接口对拍 | 同一问题分别走 `/chat` 与 `/kb/answer`，比较结论 |
| 状态机对拍 | 任务创建 → 审批 → 再查询，比较输出结构 |
| API 语义检查 | 401/403/404/409/413/422/429 是否都走统一错误信封 |

## 结果矩阵

| # | 探针 | 修复前实际行为 | 判定 | 修复 |
|---|---|---|---|---|
| 1 | 发一条文案请求后查任务详情 | `task.type = qa`（意图只进了审计日志） | 缺陷 | 路由后把意图写回任务类型 |
| 2 | 同问"支持以旧换新吗"分别走 `/chat` 与 `/kb/answer` | `/chat` **作答**，`/kb/answer` **拒答** | 缺陷（严重，对外承诺不一致） | 可答性门禁下沉到 `answer_with_context` |
| 3 | 5 个并发请求带同一 `Idempotency-Key` | 建了 **5 个任务**，返回 5 个不同 `task_id` | 缺陷（重复计费） | 原子预留 + pending 标记；进行中返回 409 |
| 4 | 携带 5 MB `options` 的请求 | **200 接受**，内存直接吃掉 | 缺陷 | 1 MB 上限 + 413 信封 |
| 5 | 审批通过后读取任务输出 | 输出被替换为 `{answer, state}`，原字段全丢 | 缺陷 | 在原输出上覆盖状态字段 |
| 6 | `idempotency_ttl_s` 是否被使用 | 只在 `config.py` 出现，**从未生效** | 缺陷（配置说谎） | 预留时按 TTL 清理过期键 |
| 7 | 3 个并发审批同一任务 | 1×200 + 2×409，审计只记 1 条 | 正常 | — |
| 8 | 8 线程并发 `counter.inc()` 共 16 万次 | 计数精确 160000 | 正常（GIL 下未观测到丢失） | — |
| 9 | `q=""`、`top_k=0`、`top_k=999`、`limit=0` | 全部 422 | 正常 | — |
| 10 | 注入语句走流式接口 | 修复前 500 `response already started`；现 422 | 缺陷（上一轮已修） | 流式响应前校验 |

## 修复后的复验

```
PASS  task.type 跟随意图  copywriting
PASS  门禁在 /chat 生效  抱歉，我在知识库中没有找到能回答这个问题的依据。
PASS  两者结论一致
PASS  并发幂等只建 1 个任务  created=1 statuses=[409, 409, 200, 409, 409]
PASS  成功响应共享 task_id  ids=1
PASS  超大 body 返回 413  413
PASS  审批后输出结构不变
```

## 新语义（已写进 README/RUNBOOK）

- **并发重复幂等键 → 409**，而不是排队等待。理由：等待会让连接被慢请求拖住，而 409 + `retry_after_s` 让客户端自己决定退避；真正的"重复计费"风险已被原子预留挡住。
- **请求体上限 1 MB**，依据 `Content-Length`；chunked 传输没有该头时，退化为字段级校验（`message` ≤ 4000 字符）。

## 已知未修

| 项 | 原因 |
|---|---|
| 多进程/多实例下的幂等与限流 | SQLite 与内存桶只在单进程内原子；水平扩展需 Redis/Postgres，已在 ARCHITECTURE 给出路径 |
| 413 对 chunked 请求不生效 | 需要在 ASGI 层边读边计数，属于网关职责（nginx `client_max_body_size`） |
| 指标计数器未加锁 | 16 万次并发递增未观测到丢失；加锁会牺牲写入路径性能，先用数据说话 |
